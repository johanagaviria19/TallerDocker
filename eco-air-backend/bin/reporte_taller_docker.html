Introducción

El presente taller tiene como objetivo encapsular el backend eco-air-backend, una aplicación Spring Boot que procesa alertas ambientales críticas, dentro de una imagen Docker de producción: ligera, segura y con cuotas estrictas de hardware. Se abordan tres retos principales: construcción multietapa con huella mínima, auditoría forense de seguridad en runtime, y calibración de límites de memoria mediante cgroups.

El backend fue desarrollado con Spring Boot 3.2.5, Java 17, base de datos H2 en memoria, Spring Data JPA y Spring Actuator. Expone endpoints REST en /api/alerts para gestión de alertas ambientales (PM2.5, CO2, NO2).

Reto 1 — Construcción Multietapa con Huella Estricta

Justificación del Dockerfile

Se implementó un Dockerfile de dos etapas para separar completamente el entorno de compilación del entorno de ejecución. La estrategia de copiar pom.xml antes que src/ aprovecha el sistema de caché de capas de Docker: si solo cambia el código fuente, la capa de descarga de dependencias se reutiliza, reduciendo tiempos de build.

Etapa 1 — builder

Imagen base: maven:3.9.6-eclipse-temurin-17-alpine

  • Se declara ARG STUDENT_ID para recibir el ID del estudiante en tiempo de construcción.
  • Se copia únicamente el pom.xml y se ejecuta mvn dependency:go-offline -B para preservar el caché de dependencias entre builds.
  • Se copia src/ y se empaqueta con mvn package -DskipTests -B.

Etapa 2 — runtime

Imagen base: eclipse-temurin:17-jre-alpine (solo JRE, sin JDK ni Maven)

  • Se crea el grupo sensorgroup y el usuario sensor_user con UID 10001.
  • Se configuran variables de entorno JVM con -XX:+UseContainerSupport y -XX:MaxRAMPercentage=75.0.
  • Se establece ENV OPERATOR_ID=907839 inyectado desde el ARG STUDENT_ID.
  • Se copia únicamente el .jar y se asigna la propiedad del directorio /app a sensor_user.
  • Se cambia al usuario sensor_user antes del ENTRYPOINT.

Comando de construcción

docker build --build-arg STUDENT_ID="907839" -t eco-air-backend:1.0.0 .

Análisis: Cada instrucción del Dockerfile genera una capa independiente. La separación entre la descarga de dependencias y la compilación permite reutilizar el caché de la capa de dependencias cuando solo cambia el código fuente, optimizando los tiempos de build subsecuentes.

2.2 Inspección del Proceso del Host — Aislamiento de Privilegios

docker run -d --name eco_air_active -p 8080:8080 eco-air-backend:1.0.0
docker top eco_air_active -o pid,user,comm
PID     USER    COMMAND
959     10001   java
Evidencia: El proceso java corre bajo el UID 10001 (sensor_user), no como root (UID 0). Esto confirma el aislamiento de privilegios configurado con USER sensor_user en el Dockerfile.

2.3 Test de Penetración — Comprobación de Inmutabilidad de Runtime

docker exec eco_air_active touch /etc/crontab_fake
touch: cannot touch '/etc/crontab_fake': Permission denied
Evidencia: El usuario sensor_user (UID 10001) no tiene permisos de escritura sobre directorios del sistema como /etc. El intento de inyectar un script malicioso fue bloqueado por el sistema operativo, validando el principio de mínimo privilegio.

2.4 Auditoría de Artefactos de Desarrollo

docker exec eco_air_active which mvn
(sin salida — comando no encontrado)

docker exec eco_air_active find / -name "*.java" 2>/dev/null
find: /root: Permission denied

Explicación: Gracias al build multietapa, la imagen de runtime no contiene Maven, el JDK ni ningún archivo .java del código fuente. Solo se copió el artefacto .jar compilado desde la etapa builder. Esto reduce drásticamente la superficie de ataque al eliminar todas las herramientas de desarrollo de la imagen de producción.

Reto 3 — Calibración de cgroups y Captura del Asesino OOM

3.1 Inducción del Colapso por Memoria (OOMKilled)

docker run -d --name eco_air_crash -m 48m eco-air-backend:1.0.0
docker inspect eco_air_crash --format='Status: {{.State.Status}} | ExitCode: {{.State.ExitCode}} | OOMKilled: {{.State.OOMKilled}}'
Status: exited | ExitCode: 137 | OOMKilled: true
Explicación: Con solo 48 MB asignados, la JVM no puede reservar el heap mínimo necesario para inicializar Spring Boot con Hibernate. El kernel Linux detecta que el proceso excede el límite del cgroup y lo termina con SIGKILL (señal 9 = ExitCode 137). El campo OOMKilled: true confirma que fue el OOM Killer del kernel quien terminó el proceso.
